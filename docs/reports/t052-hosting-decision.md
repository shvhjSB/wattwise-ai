# T052: production architecture and hosting decision

**Date:** 2026-11-02 · **Milestone:** M13 · **Decision:** D070 · **Nothing was provisioned.**

This chooses where the public WattWise application runs, using T051's measurements, prices
checked on 2026-11-02 and the owner's two answers in this task:

1. **No BDG2 data on any server.** The BDG2 licence is unresolved (D014), so neither BDG2
   readings nor a model trained on BDG2 are deployed. LEAD stays local (D022).
2. **No cost:** "deploy publicly with proper real world working website without any cost".

## Decision

| Part | Where | Cost | Card |
|---|---|---|---|
| Frontend and API, same origin | **Vercel Hobby**: the built React app as static files, the FastAPI app as one Python function | $0 | Not asked for on Vercel's pages (unverified until the owner signs up) |
| Database | **Neon Free** PostgreSQL, 1 GB | $0 | "no credit card required" (Neon pricing page) |
| Always-available fallback | The **GitHub Pages static snapshot** that is already live (T050) | $0 | None |
| The full real-data application (BDG2, LEAD) | **The owner's own machine only** (local, or the private Docker recipe, T038) | $0 | None |

What visitors would get, at no cost:

- The **labelled synthetic demo** served by the real API and database, not a recording.
- At first **read-only**: every write answers 403 (`WATTWISE_READ_ONLY`, T046).
- **Uploads analysed on the server** (data quality, the default detector's alerts, impact with an
  entered tariff) only after T058 adds sign-in and rate limits.
- Optionally, a **subset of a CC0 real dataset** (HKUST or LBNL Building 59), if the owner chooses
  it in T053.

Why this and not the others: it is the only combination found that runs the real backend and a
real PostgreSQL database for $0 without a card. Every other host that runs this backend either
asks for a card (Render, Koyeb, Fly.io), needs a paid plan (Hugging Face Docker Spaces,
DigitalOcean, Hetzner), or gives far too little credit (Railway). The details are below.

It works **within limits that must stay visible**. Vercel's free plan includes 4 CPU-hours a
month, a 4.5 MB request body and a 500 MB Python bundle. The environment as built is 623 MB, so
it must be trimmed. The plan is for personal, non-commercial use only. **None of this has been
deployed or tested yet**; T059 does that and stops if either service asks for a card.

## Measured requirements (T051 and this task)

| Need | Measured | How |
|---|---|---|
| Real BDG2 database | **6.7 GB** (readings 5.9 GB, expectations 684 MB) | T051, dev database |
| BDG2 evaluation window only (2017-06-03 to 2018-01-02) | 5,844,977 readings (29 % of 20.1 M), about **2.4 GB** with expectations and alerts | 309 bytes per stored reading, from the dev database |
| HKUST in full (CC0) | 17,419,328 readings, about **5.4 GB** at the same rate (estimate) | `data/processed/hkust/summary.json` |
| Synthetic demo database | 5,376 readings, a few MB (estimate: under 2 MB of readings at 309 bytes each) | Sample size |
| Promoted BDG2 model | 49 MB | Registry (not deployable: trained on BDG2) |
| API memory, read-only requests | **279 MiB peak** after 86 requests on real BDG2 data (213 MiB after imports) | Windows process counters, this task |
| API memory, upload analysis at its limits | **552 MiB peak** for 48 meters and 193,536 rows, answered in 20 s | Same, `POST /api/v1/inference/analyze` |
| Public image under Render's free limits | 176 MiB at 0.1 CPU / 512 MB | `deploy/render/verify.sh` (T051) |
| Python environment, Linux | **623 MB** (pyarrow 167, scipy 109 + 30 libs, pandas 72, scikit-learn 48, numpy 43 + 27 libs, SQLAlchemy 23, uvloop 16, holidays 13, LightGBM 10) | `du` inside the public image |
| Upload size per reading | 81.7 bytes per row in the canonical CSV | Synthetic sample |

Consequences:

- **512 MB of memory is enough for read-only use but not for uploads near the limits** (552 MiB).
- No free database holds the real BDG2 data (6.7 GB) or full HKUST (about 5.4 GB). The BDG2
  evaluation window alone (about 2.4 GB) does not fit either.
- The analysis figure used the BDG2-trained model from the local registry. A public server would
  use the synthetic demo model, so its memory has to be measured again in T059.

## Licences: what may be public

| Data | Public on a server? | Reason |
|---|---|---|
| BDG2 readings, and models trained on them | **No** | Owner's answer in this task; licence unresolved (D014) |
| LEAD labels | **No** | Local evaluation only (D022) |
| Synthetic sample | **Yes**, labelled synthetic | Generated by WattWise |
| HKUST campus meters (Dryad) | **Allowed**: CC0, about 5.4 GB in full, so a subset at most | DATASETS.md:667 |
| LBNL Building 59 (Dryad) | **Allowed**: CC0, one building | DATASETS.md:665 |
| ERA5 weather for HKUST | **Allowed** with attribution: CC BY 4.0 | DATASETS.md:371 |

So **a public read-only historical demo is feasible within licences, but only with CC0 data**,
not BDG2 or LEAD. Two conditions apply:

- It must be a subset that fits the free database. At 309 bytes per stored reading, for example,
  50 HKUST meters over 2.4 years is about 1 million readings, roughly 0.3 to 0.4 GB with
  expectations (estimate).
- Expected consumption must come from a model not trained on BDG2. The HKUST evaluation (T041)
  used the BDG2 model, so a public HKUST demo would show the readings, the model-free default
  detector and the baselines, or a model trained on HKUST's own training window.

Whether to add a CC0 real subset at all is the owner's choice in T053.

## The chosen option's limits and what is unverified

| Limit | Effect on WattWise | Handled in |
|---|---|---|
| **4 active CPU-hours a month**; over the limit, the Hobby plan blocks the feature for up to 30 days ("you will have to wait until 30 days have passed") | Read-only requests are cheap. One visitor could still use up the month: 14,400 CPU-seconds is 720 analyses at the measured 20 s for 193,536 rows (smaller uploads cost less). **So uploads stay off until T058 adds sign-in and per-user rate limits**, and the Pages snapshot stays up as the fallback | T058, T059 |
| **4.5 MB request body** | Uploads up to about 55,000 readings (81.7 bytes per row), against about 122,000 under today's 10 MB default; `WATTWISE_MAX_UPLOAD_BYTES` must be lowered to about 4 MB there | T059 |
| **500 MB Python bundle (uncompressed)**; the environment is 623 MB | pandas 3 does not require pyarrow, and the Parquet readers found are on training and loading paths, so pyarrow (167 MB) and uvloop (16 MB) may not be needed at request time; without them it is about 440 MB (not yet tried). If that does not work, Vercel's "large functions" (beta, up to 5 GB) is the alternative | T059, which must show a working bundle |
| **Personal, non-commercial use only** (Hobby) | Fine for a personal portfolio project. Commercial use would need a paid plan | Owner |
| No shared memory between function instances | Rate limits and sessions must be stored in PostgreSQL, not in process memory | T058 |
| Neon sleeps after 5 min idle; 100 CU-hours a month; 5 GB egress a month | The first request after a pause waits for the database to wake; cold starts are not measured | T059 |
| Filesystem and `/tmp` behaviour not stated on Vercel's pages | The app must not write next to its code; the demo model must be built into the bundle in CI | T059 |
| **"No card" is the providers' statement, not yet the owner's experience** | Render's free plan was also expected to need no card. If Vercel or Neon asks for one, T059 stops and the Pages snapshot stays the public site | T059 |

The application code does not change for this. The same FastAPI app already runs in the Render
image, the private Docker recipe and the tests. Moving later to a paid host, with the owner's
approval, needs no rewrite.

## What this changes in the roadmap

- **T053:** the owner decides whether a CC0 real subset (HKUST or LBNL Building 59) joins the
  public synthetic demo. Never BDG2 or LEAD.
- **T058:** sign-in and rate limits stored in PostgreSQL, required before public uploads on a
  4 CPU-hour budget.
- **T059:** deploy on Vercel Hobby + Neon Free. The owner's actions at that point:
  1. Sign in to Vercel with the `shvhjSB` GitHub account and import the repository.
  2. Create a Neon Free project.
  3. Put its connection string into Vercel's environment settings, which Claude cannot do.

  If either asks for a card, stop.
